# Technical transport addendum v2.3: one indexed temperature message per initial range

Fixed before use. The scientific sample, thresholds, bounds and reporting strata remain unchanged. Current 262144-byte chunks require about three public HTTP requests per roughly0.6MB temperature field. Observed completed mixed jobs take approximately3–7minutes per fifty-member unit, including extraction and subset LPs. The city/time boundary requires four units per horizon; reducing avoidable request overhead helps complete the already fixed design within the trial deadline.

Allow chunk size1048576bytes. A temperature message smaller than this limit is requested in one ordinary Range GET, using its exact already indexed offset and length. No whole multi-gigabyte object is fetched. The same validation, per-endpoint attempt limit, two-level failed-range subdivision, lower size bound, official hosts, no403/404 or ignored-Range recovery, strict complete-body/GRIB checks and maximum two acquisition invocations per unit remain. No additional fields, providers, loops, permission route or scientific hypothesis are added. This is ordinary retrieval of fixed public inputs, not a load test or a study of server performance.

First use is the first already planned city/time date-model-horizon job. Its actual runtime will determine whether later jobs can include both horizons while remaining below1800seconds; do not infer a server performance effect from an uncontrolled timing comparison.
